# 照片应用第一版：先理解一条流程

状态：本地已实现并验证，AWS 动态资源尚未创建。使用现有五张本人照片，更多照片由本人另选。

## 先看什么

当前本地地址为 http://127.0.0.1:8766/photos/index.html?lang=zh 。服务停止后，在项目目录执行：

```powershell
pwsh -File ./scripts/Start-PhotoPreview.ps1 -OriginalDirectory 'E:\醒图\醒图'
```

浏览器查看预览、切换语言，选择一张下载。下载的是 JPG 原文件，预览为已有 WebP。页数来自分页结果；现在五张不足一页，上一页/下一页禁用是正常情况，不补造更多作品。

第一版只需要先串起这条流程：

1. 浏览器请求 `/api/photos`。
2. 读取器按顺序取最多 24 条照片资料，返回三语标题、预览位置、原图位置、大小与下一页标记。
3. 页面展示预览。点击下载时，浏览器直接请求原 JPG，不让图片经过数据库或资料读取函数。

本地的第 2 步从 `.local/photo-app/catalog.json` 读取，是替身；AWS 部署后改用 Lambda 对 DynamoDB 的 `Query`。本地页面有明确提示，不代表已经验证 AWS 数据库或邀请权限。部署后页面与 JPG 均经既有 CloudFront 邀请保护。

## 文件怎么分工

| 文件 | 作用 |
| --- | --- |
| `config/photo-selection.json` | 明确选择的五张照片、ID、顺序与标题键；不会扫描原图目录把所有照片导入 |
| `scripts/prepare-photo-data.cjs` | 读取现有三语标题，计算原 JPG 大小和 SHA256，生成本地目录与 DynamoDB 批次 |
| `dist/photos/content.js` | 新界面三语文字；原求职页 `dist/content.js` 的本人试改未改动 |
| `dist/photos/app.js` | 读一页资料、翻页、大图预览与原 JPG 下载 |
| `backend/photo-api/core.mjs` | 分页输入检查、返回字段限制与错误处理 |
| `backend/photo-api/index.mjs` | Lambda 入口，真正调用 DynamoDB；尚未云端运行验证 |
| `scripts/photo-dev-server.mjs` | 仅监听本机的预览与文件读取，不连接 AWS |

`.local/` 中的资料、上传副本、ZIP 和截图均不进入 GitHub。原 JPG 不放进 `dist/` 或源码仓库。已有少量 WebP 展示图仍保留在仓库。

现有五张标题从已维护的求职页三语文案初始化。以后新增照片可在选择清单每项中提供 `title: {ja, zh, en}`，不必继续增加求职页的文案键；照片说明译文需本人确认。改本地文字不会自动修改已导入的 DynamoDB 资料，需按资料维护流程更新。

## 一条照片资料

```json
{
  "PK": "ALBUM#main",
  "SK": "PHOTO#000000001#fuji-lake",
  "id": "fuji-lake",
  "title": {"ja": "湖畔と富士山", "zh": "湖畔与富士山", "en": "Mount Fuji by the lake"},
  "previewKey": "assets/photos/IMG_8655.webp",
  "originalKey": "photo-originals/main/fuji-lake.jpg",
  "filename": "IMG_8655.JPG",
  "sizeBytes": 19423722
}
```

实际资料另含 `sha256`，用于对照下载完整性。PK 是相册归属，SK 把顺序和照片 ID 合在一起。接口固定读 main 相册，最多 24 条；下一页标记只允许继续这个相册，不接受任意表、相册或用户指定的大页数。没有 `Scan` 或数据库写接口。

每页 24 张不是“百万图片已验证”。以后数据增多仍使用分页，热点、索引、配额、并发与费用需按实际请求量另验证。

## 之后按这三组部署（由本人操作）

### 1. DynamoDB 表与照片资料

- 东京区建一张 `cj-photo-catalog` 表，分区键 `PK`（String），排序键 `SK`（String），按需容量，不加首版不需要的索引/全局副本。
- 表只保存资料，不上传图片二进制。实际可用配置、吞吐上限及费用在控制台核对。
- 批量资料由本地准备脚本生成，每批最多 25 条。首次向空表导入后核对记录数和标题。
- 控制台没有直接导入这份 BatchWriteItem JSON 的按钮；建议在控制台内 CloudShell 上传 `batch-001.json` 后运行下面命令。这是需本人执行的 AWS 写入操作，先核对身份、区域与表名，再执行；本轮助手没有运行。

```bash
aws dynamodb batch-write-item --region ap-northeast-1 --request-items file://batch-001.json
```

返回的 `UnprocessedItems` 必须为空。非空时保留未处理内容、间隔后重试，不能把 HTTP 成功视为全部导入；不要未经核对反复导入不同清单。相同 PK/SK 的 Put 会覆盖已有资料，未列出的旧资料不会自动删除。多批按编号分别核对，不使用目录中未经确认的旧文件。

### 2. 只读 Lambda 与受保护接口

- Lambda 名称建议 `cj-photo-api`，Node.js 24.x，处理器 `index.handler`，环境变量 `PHOTO_TABLE=cj-photo-catalog`、`PHOTO_ALBUM=main`。从 `photo-api.zip` 上传代码，ZIP 根目录为两份 mjs，使用运行时内置 AWS SDK v3。
- 执行身份仅需对该表 main 相册的 `dynamodb:Query`，模板在 `backend/photo-api/read-policy.example.json`；替换账号 ID。Lambda 运行日志另需相应权限及保留天数，不加入 Log Check 联动。函数不需要 S3 读取/写入权限。
- 入口方案为 Lambda Function URL（`AWS_IAM`）+ Lambda 类型 CloudFront OAC，经现有分配新增 `api/*` 行为。该行为必须限制查看器访问并选择现有可信密钥组；缓存使用 CachingDisabled，仅允许 GET/HEAD，不沿用 S3 缓存策略。
- 源站使用函数 URL，不添加 origin path；OAC 使用 Always sign。回源 Host 不透传查看器 Host，可用 AllViewerExceptHostHeader。S3 类型 OAC 不复用于 Lambda。
- 必须同时授予指定 CloudFront 分配 `lambda:InvokeFunctionUrl` 与 `lambda:InvokeFunction`，资源策略限定现有分配 `E1EXJ282JJY07Q` 的 SourceArn。官方说明这项权限修改需要 AWS CLI；拟由本人在 CloudShell 执行，账号 ID 与实际函数建立后再生成准确命令，不用静态 Access Key。
- 未签名函数 URL 直连应拒绝。有 AWS 管理权限的本人不等同于未获邀普通访客；不把管理员可调用当成访客绕过。
- 最终需实际验证：有效邀请接口返回资料；无邀请、过期邀请及匿名源站直连拒绝。Cookie 不写入日志，错误仅返回稳定代码，前端选择三语提示。

### 3. 上传文件、费用提醒与集中验收

运行 `pwsh -File ./scripts/Prepare-PhotoDeployment.ps1` 只生成本地材料。每次使用新的 `.local/photo-app/deploy-时间/` 目录，避免混入旧选择；内含 `photo-api.zip`、本次 batch 文件、上传计划及原 JPG 副本。

- 在现有 S3 桶根目录添加准备目录中的 `photo-originals/` 文件夹，保留子目录。副本以照片 ID 命名，原目录文件不改名、不修改字节。
- 新页面 `dist/photos/` 上传至桶根目录的 `photos/`。原求职首页暂未增加入口，先用 `/photos/index.html` 直接验收；通过后再加入入口，不先把未上线功能宣传成已可用。
- 预览图复用现有 `assets/photos/`。现有 S3 私有/OAC 和默认邀请行为继续保护页面与原图，无需新桶或重复 CloudFront 分配。
- 预算目标 USD 5/月，费用提醒不是硬停止；部署时核对按需吞吐上限、Lambda 超时/并发和日志保留，提醒阈值与通知邮箱由本人在账单控制台设置。此前日常身份账单权限问题仍暂放，设置若受限再处理，不升级账号。
- 集中验收：三语及分页/异常提示；有效与无效访问；原 JPG 实际保存、字节及哈希；当前用量和费用设置。没有验证的步骤保持待验收。
