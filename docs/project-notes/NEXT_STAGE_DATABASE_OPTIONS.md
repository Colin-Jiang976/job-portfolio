## 三种数据方案的比较

| 方案 | 适合的情况 | 可练习内容 | 需要承担的工作 |
| --- | --- | --- | --- |
| 保留静态 JS/JSON | 内容少、低频修改、主要展示和下载 | 文件组织、版本、部署和缓存更新 | 修改后同步网站；没有数据库读写实践 |
| DynamoDB | 可按 ID/相册等明确访问方式组织的小型动态资料 | 主键、查询模式、IAM、后端读取与错误处理 | 先设计查询与键；不支持关系型 JOIN；容量模式及费用需核对 |
| RDS（如 PostgreSQL/MySQL） | 明确希望练 SQL、关系数据和关联查询 | 表关系、SQL、网络与数据库访问管理 | 数据库实例/存储、网络连通、凭据、备份和费用配置；对当前五张照片而言部署面更大 |

没有选定访问方式前，不确定表名、主键、数据库引擎或容量模式。若最终只需一小份相册资料，可优先评估 DynamoDB；若学习重点是 SQL 和关系建模，RDS 仍是合理选项。上述为建议，不是本人已选择。

DynamoDB 是托管的无服务器 NoSQL 数据库，支持按需或预置容量；按需读写计费不等于所有相关项目免费。RDS 托管常见关系型引擎，但仍需选择实例、存储、网络和数据库访问方式。部署前根据选定配置与实际免费账号权限核对费用；不升级账号、不承诺免费计划或抵扣覆盖。

## 网站读取数据库的候选路径

浏览器请求受保护的接口，由后端读取数据库后返回必要数据。数据库凭据或长期 AWS Access Key 不放进前端。读接口和管理写接口的权限应分开，持有求职邀请链接不代表可以修改资料。

候选入口需要另选：

- Lambda Function URL + CloudFront OAC：可评估让现有分配的 `/api/*` 行为先检查访客签名 Cookie，再由 OAC 认证回源。Function URL 使用 AWS_IAM，限制到既有分配，防止绕过 CloudFront。Lambda 源站需要对应的 OAC，不能直接复用 S3 类型设置；资源策略配置可能需要 CLI。
- API Gateway + Lambda：适合需要更多路由和接口管理的情况；HTTP API 与 REST API 的功能、权限和价格不同。仍须设计直连接口的授权，不能只在网页上加邀请限制。

两种均未选择、未部署。现有邀请机制的签名范围为当前 CloudFront 域名 `/*`，新接口路径也必须使用受保护行为；动态接口的缓存、返回字段和错误提示需单独设计。新增三语界面与提示仍保持日中英。
