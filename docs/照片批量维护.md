## 准备一批照片

### 固定双击入口（2026-10-28新增）

在job-portfolio根目录双击 `Photo-Maintenance.cmd`。无需打开PowerShell或复制Python路径，不修改执行策略。

- 输入1并回车：打开固定选图文件夹 `.local/photo-app/new-input`。
- 将本次新JPG复制进去，输入2并回车：检查、生成新照片材料，并打开结果文件夹。已在本地已发布快照中的相同原图会跳过；不会清空输入目录或更改原文件。若全都已发布，会提示没有重新打包。
- 输入3并回车：打开最近一批材料；还没有新草稿时，打开最近已发布批次。
- 输入4并回车：使用AWS官方浏览器登录，然后自动读取账号/身份。使用独立photo-maintenance配置、东京区域，不创建长期访问密钥、不改IAM权限、不发布照片。当前电脑AWS CLI 2.38.4已安装，本人已于10/29完成登录；会话失效后再使用4。若权限不足，保留错误反馈，不自行增加管理员权限。
- 输入5并回车：读取最近新批次，先只读核对登录身份、桶归属、表和本批已完成项，展示目标和数量。本人输入大写PUBLISH后才开始S3上传和DynamoDB登记；直接回车取消。已在本地发布记录中的旧批次会直接跳过，不重传。登录已于10/29由本人完成，菜单4中的额外AI skills/MCP配置是AWS官方CLI可选提问，选择n跳过即可，工具不依赖这些集成。
- 输入0并回车：退出。

启动菜单本身不联网。1/2/3为本地操作；4登录/读取身份；5只有本人确认后才写入固定AWS目标。工具仅支持当前一个维护者新增照片，不能当作公众/多人上传系统，不创建资源、改权限或删除云端图片。入口使用本机现有Codex捆绑Python、图片依赖及AWS CLI，发布目标身份/账号绑定在忽略目录.local/photo-app/publish-target.json，尚不是任意电脑的安装包。同键资料编辑仍另用明确清单。

### 一次完整新增（统一入口）

1. 重新双击Photo-Maintenance.cmd，选1，把真正想新增的JPG复制进选图文件夹；已发布旧图留在里面也会跳过。
2. 选2生成材料；它会打开本次结果文件夹，可看s3内预览和原图副本。
3. 选5，核对显示的桶、表、区域及新增数量，再输入PUBLISH。工具先上传全部图片、核对内容，然后登记资料，最后核对并推进本地已发布记录。无需手动传CloudShell文件或逐批粘贴数据库命令。
4. 本批完成后，在原获邀浏览器刷新线上相册，集中反馈最终输出/显示数量；中途报错保留结果，不用逐步等待确认。

发布时同名不同内容、同键不同资料会拒绝覆盖；图片用S3条件写入，资料用DynamoDB条件PutItem。中途失败保留已完成项，不自动回滚/删除，也不把未核对批次设为已发布；重试同一批会读取云端已完成项并跳过匹配内容。结果在本批publish-result.json；若本地快照和云端末尾位置不同，会停止要求同步，不盲目继续编号。

### 保留的命令行入口

在 job-portfolio 目录运行（路径替换为本次输入目录；当前已准备好五样本，无需重跑）：

```powershell
./scripts/Prepare-PhotoDeployment.ps1 -OriginalDirectory '本批JPG目录'
```

如果 Windows PowerShell 提示“在此系统上禁止运行脚本”，PS入口尚未启动。可直接运行同一个Python核心，不需更改执行策略。本机已核对Codex捆绑Python存在：

```powershell
$photoPython = Join-Path $env:USERPROFILE '.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe'
& $photoPython -X utf8 '.\scripts\prepare_photos.py' '本批JPG目录'
```

Python入口的 `--output` 对应PS入口的OutputDirectory，`--selection` 对应SelectionPath，`--baseline` 对应BaselinePath；只是入口不同，准备逻辑相同。

- 不用改源码、不用填写标题。JPG/JPEG 扩展名大小写均可，支持中文/空格文件名。目录内全部 JPG 都视为本次选择，因此应先把要处理的照片集中在一个目录；不递归读取子目录。
- 新照片 ID 为原图 SHA256 前 24 位加 p-，顺序默认接在基准之后，按文件名排序。相同内容换名后仍识别为同一照片。本批同一原图重复出现会报错。
- 默认优先使用 `.local/photo-app/published-catalog.json`（当前已发布8条），不存在时才用旧 `.local/photo-app/catalog.json`；**不是实时读取 AWS**。新增一批全部发布核对后再接续已发布快照，不把未发布草稿自动当基准。也可用 `-BaselinePath '已发布批次目录/baseline-after.json'` 显式指定。不同草稿不能分别用旧基准独立发布，应先基于同一已发布快照重新准备并核对。
- 可用 `-SelectionPath './config/photo-selection.json'` 选择明确清单，保持五样本的 ID、顺序与原路径。自定义清单结构相同，title/captionKey 可省略，title 可为单一名称、部分译名或 null；不自动翻译。
- 同一 ID 改原图、顺序或预览键，以及不同 ID 占用同一顺序/预览键/原图，都会拒绝。本轮支持批量新增与同键资料更新；删除、重排和替换原图另行处理，避免旧 SK 留下重复照片。

## 输出与核对

成功输出在 `.local/photo-app/batches/时间-编号/`，也可通过 `-OutputDirectory` 指定 `.local/` 内尚不存在的目录。输出拒绝覆盖；失败目录以 `.incomplete-` 开头，不能用于发布。所有准备材料均被 Git 忽略。

| 文件 | 用途 |
| --- | --- |
| `s3/assets/photos/*.webp` | 最长边不超过 1800 的预览，校正 EXIF 方向，不加滤镜；已有可用预览复用原字节 |
| `s3/photo-originals/main/*.jpg` | 原 JPG 的逐字节副本，以 ID 命名，大小/哈希与资料核对 |
| `catalog.json`、`selection.json` | 本次资料和选择清单，可供检查/重用 |
| `batch-001.json` 等 | 仅本次照片的 DynamoDB PutRequest，每文件最多 25 条，无旧批次残留 |
| `manifest.json` | 精确 S3 对象键、大小、SHA256、表名、本次条数和应导入文件列表 |
| `baseline-before.json`、`baseline-after.json` | 已知基准与本批合并后的候选快照；未选择的旧照片仍保留 |
| `source.json` | 本机预览读取批次副本的位置，不上传云端 |

本次批量准备不包含 Lambda ZIP 或页面更新。用以下命令看本次照片，原图下载也读取包内副本：

```powershell
./scripts/Start-PhotoPreview.ps1 -PreparedDirectory '成功输出目录' -Port 8772
```

打开 `http://127.0.0.1:8772/photos/index.html?lang=zh`。本地预览只显示本批选择，**不表示线上相册将只剩这些照片**。默认日文及三语界面沿用原页面。关闭终端后服务停止，可运行上面的命令恢复。

## 发布时由本人执行

以下为原手动控制台/CloudShell备用方式；统一入口首次真实发布核对后，日常可使用上面的菜单5。

当前五张完全相同，**不需要发布本次样本包**。以后真正新增时，助手继续逐环节解释并核对，不要求本人自行通读完成：

1. 对照 manifest 核对本批、现有云端资料和目标桶。将 `s3/` **内部的** `assets/`、`photo-originals/` 放到原桶根；不能带外层 `s3/`，不能省掉 `photo-originals/`。本地冲突检查不保证云端无同名对象，上传前核对。
2. 图片到位后，在原账号/东京区核对表名，按 manifest 列出的文件执行 BatchWriteItem。每次检查 `UnprocessedItems`；非空表示尚未全部完成，只重试未处理项，不能据返回成功就确认全部导入。
3. Put 会替换同 PK/SK 的整条资料，包括标题；清单未列出的旧资料不会删除。只在本批全部完成并按新路径验证后，将 baseline-after 作为下批基准；不因本地准备成功就替换已发布基准。

新增独立对象键通常无需失效旧路径；更新既有对象时再按实际变更定向失效。只验证本次新增/变更范围，不重复首版17项或首页旧验收。
