# 照片下载排查

先比较“网页请求的对象键”和“S3 实际对象键”，不要看到 403 就立即改权限。

## 下载路径从哪里来

1. 本地 `scripts/prepare-photo-data.cjs` 为照片生成 `originalKey`，例如 `photo-originals/main/fuji-lake.jpg`，写入批量导入材料。
2. 导入后，DynamoDB `cj-photo-catalog` 中该照片项目的 `originalKey` 保存这个值。
3. Lambda 读取它并验证格式，在前面加 `/`，返回 `downloadUrl`。
4. 相册下载按钮使用这个地址；CloudFront 按行为路由向 S3 读取对应对象。资料中的路径不会自动创建 S3 对象。

## 不看代码也能核对

1. 用有效邀请进入网站，在同一浏览器打开 `/api/photos`，搜索照片 ID，例如 `fuji-lake`，查看该项目的 `downloadUrl`。
2. 在 S3 的现有桶中找到对应 JPG，打开对象详情，查看“键（Key）”。
3. 将 `downloadUrl` 开头代表网站根路径的 `/` 去掉后，与 S3 键逐字比较；目录层级、大小写、扩展名都要一致。
4. 如果下载失败，可复制按钮链接到同一浏览器的新标签页，查看具体报错。`MissingKey` 表示缺少 CloudFront 所需的签名参数或 Cookie；重新使用完整邀请入口。`AccessDenied` 不能单独证明权限错误：先确认对象存在且键一致，再排查源站权限/加密/缓存等。

`filename`（例如 `IMG_8655.JPG`）是建议保存到电脑时的文件名；`downloadUrl` 是服务器上的请求地址，两者不同是当前设计。

## 本次案例（2026-10-26）

- 页面及预览正常，下载失败；独立有效邀请请求得到预览 206、原图 S3 AccessDenied 403。
- 下载地址要求 `photo-originals/main/fuji-lake.jpg`，本人核对实际键为 `main/fuji-lake.jpg`，缺少前缀；没有证据表明传错桶。
- 指导将五张 JPG 复制到同桶 `photo-originals/main/` 后，本人反馈“这次成功了”。尚未逐张独立验证全部原图的字节/哈希；旧位置副本是否保留待核对。
- 上传时哪一步导致前缀缺失尚未确定。以后上传完成核对实际对象键，不能仅凭本地文件夹名推断。
